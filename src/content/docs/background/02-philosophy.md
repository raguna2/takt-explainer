## 「強制力」という設計原則

taktの最も根本的な設計原則は、**「強制力による品質担保」**です。この原則は、AIエージェントとの協業において、多くの開発者が直面する本質的な問題に対する回答です。

### 「お願い」と「強制」の違い

従来のAIエージェント運用では、品質を担保するための手段は主に**プロンプトへの指示**でした。

```
# 従来のアプローチ: プロンプトで「お願い」する
あなたはシニアエンジニアです。
以下のルールに従ってコードを書いてください：
- 必ずテストを書くこと
- セキュリティを考慮すること
- コーディング規約に従うこと
- レビュー観点でセルフチェックすること
```

このアプローチの問題は、指示の遵守が**AIの判断に依存する**ことです。AIはこれらの指示を「理解」はしますが、以下のような理由で遵守しないことがあります。

- **コンテキストウィンドウの制約**: 会話が長くなると、初期の指示が文脈から押し出される
- **指示の競合**: 「速く実装して」と「テストを書いて」が実質的に競合する場合、AIはどちらかを優先する
- **解釈の揺れ**: 「セキュリティを考慮する」の具体的な意味がAIの判断に委ねられる
- **忘却**: 単純に指示を見落とす、または無視する

taktはこの問題を根本から解決します。品質担保のステップをプロンプトへの指示ではなく、**ワークフローの構造として組み込む**のです。

```yaml
# taktのアプローチ: ワークフローとして「強制」する
movements:
  - name: implement
    persona: coder
    edit: true
    # coderペルソナはコードを書くことだけに集中

  - name: security-review
    persona: security-reviewer
    edit: false
    # セキュリティレビューは別のペルソナが「必ず」実行する
    # coderがセキュリティを「考慮し忘れる」ことは構造的に不可能

  - name: test-review
    persona: qa-reviewer
    edit: false
    # テストの検証も別ペルソナが「必ず」実行する
```

この設計では、セキュリティレビューやテスト検証は**スキップ不可能なステップ**として存在します。coderペルソナがセキュリティを見落としても、security-reviewerペルソナが必ず検証を行います。これが「お願い」ではなく「強制」による品質担保です。

### 確定的遷移 vs AI判断

taktのもう一つの重要な設計判断は、ワークフローの遷移を**AIの判断ではなくルールに基づいて決定する**ことです。

多くのマルチエージェントフレームワークでは、「次にどのエージェントに仕事を渡すか」をAIが動的に判断します。これはClaude CodeのSwarmのような動的協調モデルに代表されます。柔軟性は高いですが、実行のたびに異なるフローが発生し、再現性が低くなります。

taktでは、遷移は**Pieceの定義に記述されたルール**によって決定されます。

```yaml
rules:
  - condition: 実装完了
    next: review
  - condition: 続行不能
    next: ABORT
```

taktのエンジンは、このルール定義から自動的にステータス判定プロンプトを生成し、AIの出力を解析して次の遷移先を決定します。AIが出力する内容は自由ですが、**遷移の決定権はtaktのエンジンにあります**。これにより、以下が保証されます。

- 同じPieceを実行すれば、必ず同じ順序でステップが実行される
- レビューで問題が検出されれば、必ず修正ステップに差し戻される
- 全ステップが正常に完了しない限り、ワークフロー全体は完了しない

## 音楽メタファの意図

taktは音楽用語を全面的に採用しています。これは単なる命名の趣味ではなく、意図的な設計判断です。

### Takt（タクト）= 指揮棒

ツール名の「takt」はドイツ語で指揮棒（Taktstock）を意味します。オーケストラにおいて、指揮者は楽譜に基づいて各演奏者のタイミング、強弱、テンポを統制します。演奏者は各自の技術で演奏しますが、**全体の構成と流れは指揮者が決定**します。

taktとAIエージェントの関係はまさにこれと同じです。

| 音楽 | takt |
|---|---|
| 指揮者 | taktエンジン |
| 楽譜 | Piece（YAML定義） |
| 演奏者 | Persona（AIエージェント） |
| 楽章 | Movement（ステップ） |
| 演奏 | タスクの実行 |

### Piece（ピース）= 楽曲

Pieceはtaktにおけるワークフロー定義の単位です。楽曲が複数の楽章から構成されるように、Pieceは複数のMovementから構成されます。楽曲が「どの楽器が、いつ、何を演奏するか」を規定するように、Pieceは「どのペルソナが、いつ、何を行うか」を規定します。

楽曲を一度作曲すれば何度でも演奏できるように、Pieceを一度定義すれば何度でも実行できます。同じ楽曲を異なるオーケストラが演奏できるように、同じPieceを異なるプロジェクトで使い回すことができます。

### Movement（ムーブメント）= 楽章

Movementは楽曲内の各セクションです。交響曲の第1楽章が「提示部」、第2楽章が「展開部」であるように、コードレビューPieceの第1 Movementが「実装」、第2 Movementが「レビュー」に対応します。

各楽章には独自の調性やテンポがあるように、各Movementには独自のペルソナと命令テンプレートがあります。楽章間の移行が作曲者によって決められているように、Movement間の遷移はPiece定義のルールによって決められています。

### Persona（ペルソナ）= 演奏者

Personaは特定の役割を持つAIエージェントの定義です。ヴァイオリニストがヴァイオリンの演奏に特化しているように、coderペルソナはコード実装に特化し、security-reviewerペルソナはセキュリティ検証に特化しています。

各演奏者が楽譜の自分のパートだけを演奏するように、各ペルソナはMovementで割り当てられたタスクだけを実行します。全員が全パートを演奏しようとすると混乱が生じるように、1つのAIに全ての役割を担わせると品質が低下します。

### メタファの効果

音楽メタファの採用は、以下の効果をもたらします。

1. **概念の理解しやすさ**: 「ワークフロー」「ステップ」「ロール」といった抽象的な概念が、楽曲・楽章・演奏者という具体的なイメージで直感的に理解できる
2. **設計の一貫性**: 音楽メタファに沿って設計することで、各概念の関係性が自然に整理される
3. **拡張の方向性**: 新しい機能を追加する際、音楽メタファに沿った命名と設計が自然に導かれる

## 分離と結合のバランス

taktの設計は、ソフトウェア工学の基本原則である「関心の分離」（Separation of Concerns）を強く意識しています。

### プロンプトの分離: ファセットプロンプティング

従来のAIエージェント運用では、プロンプトは一つの長大なテキストとして管理されることが多くありました。役割の定義、コーディング規約、タスクの指示、ドメイン知識、出力フォーマットなどが一つのプロンプトに混在していました。

taktは**ファセットプロンプティング**（Faceted Prompting）という設計パターンを採用し、プロンプトを5つの独立したファセット（関心事）に分離します。

| ファセット | 内容 | 変更頻度 |
|---|---|---|
| **Persona** | 役割・専門性の定義 | 低（一度定義すれば安定） |
| **Policy** | コーディング規約・品質基準 | 中（プロジェクトの方針変更時） |
| **Instruction** | Movement固有の手順 | 高（タスクごとに異なる） |
| **Knowledge** | ドメイン知識・アーキテクチャ情報 | 中（設計変更時） |
| **Output Contract** | 出力フォーマットの定義 | 低（一度定義すれば安定） |

この分離により、以下が実現されます。

- **保守性**: コーディング規約（Policy）を一箇所変更すれば、全Pieceに自動的に反映される
- **再利用性**: 同じPersonaを異なるPieceで使い回せる
- **テスト容易性**: 各ファセットを独立してテスト・検証できる
- **チーム協業**: 異なるメンバーが異なるファセットを担当できる

### 役割の分離: ペルソナシステム

ペルソナの分離は、ソフトウェア開発における「単一責任原則」のAIエージェント版です。

一つのAIに「コードを書いて、レビューして、テストも確認して、セキュリティもチェックして」と指示すると、各責務の遂行品質が低下します。人間のチーム開発でも、同一人物が実装者とレビュアーを兼ねることは推奨されません。

taktでは、各ペルソナが**一つの責務に特化**します。coderペルソナはコードの実装品質に集中し、security-reviewerペルソナはセキュリティの観点に集中し、supervisorペルソナは全体の整合性に集中します。

### 定義と実行の分離

Piece（定義）とPieceEngine（実行）の分離も重要な設計判断です。Pieceはワークフローの「何を」を定義し、PieceEngineは「どのように」を担います。

これにより、同じPiece定義を異なるプロバイダー（Claude、Codex等）で実行したり、異なるモデル（opus、sonnet等）で実行したりすることが可能になります。ワークフローの定義とAIの実行環境が疎結合であることで、柔軟な運用が実現されます。

## 動的協調との対比

taktの設計思想をより深く理解するために、対照的なアプローチと比較してみましょう。

### Claude Code Swarm: 動的協調

Claude CodeのSwarmは、複数のAIエージェントが動的に協調するモデルです。エージェントは必要に応じて他のエージェントを呼び出し、タスクを委譲し、結果を統合します。協調のパターンは事前に定義されるのではなく、実行時に動的に決定されます。

**メリット**: 未知のタスクや探索的な作業に対する柔軟性が高い
**デメリット**: 再現性が低く、品質の保証が困難

### takt: 確定的オーケストレーション

taktは事前定義されたPieceに基づく確定的な実行を行います。フローの分岐は存在しますが、分岐条件はPiece定義に記述されたルールに従います。

**メリット**: 再現性が高く、品質を構造的に保証できる
**デメリット**: 事前に定義できないタスクには対応しにくい

### 使い分けの指針

taktはすべてのAI作業を置き換えるものではありません。**定型的な開発フロー**——コード実装→レビュー→修正→承認といった、パターンが確立されたワークフロー——に特化しています。

一方、「どのアプローチが最適か分からない」「要件が曖昧で探索が必要」といった非定型タスクでは、動的協調モデルの方が適しています。

taktの作者自身も、探索的なタスクにはClaude Codeを直接使い、定型的な開発フローにはtaktを使うという使い分けを実践しています。

## セルフドッグフーディング

taktの設計思想を体現する最も強力な証拠は、**takt自体がtaktを使って開発されている**という事実です。

taktのコードベースの変更は、taktのPieceを通じて実行されます。コーダーペルソナが実装し、レビュアーペルソナがレビューし、スーパーバイザーペルソナが承認する——このフローがtakt自身の開発に適用されています。

さらに、taktの作者はtaktを使ってZennの技術記事の執筆まで行いました。著者エージェントが文章を書き、専門知識レビュアーが技術的正確性を検証し、編集エージェントがスタイルガイドへの準拠を確認する——という、ソフトウェア開発と同様のレビューサイクルを文章執筆に適用しています。

このセルフドッグフーディングは、taktの設計思想が理論だけでなく実践において機能していることの証明です。
