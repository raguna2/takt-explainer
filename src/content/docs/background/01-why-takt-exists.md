## AIコーディングエージェントの時代

2024年から2025年にかけて、AIコーディングエージェントは急速に実用化されました。Claude Code、GitHub Copilot、Cursor、OpenAI Codexといったツールは、自然言語の指示からコードを生成し、テストを実行し、デバッグまで行えるようになりました。開発者の生産性は飛躍的に向上し、「AIに任せればコードが書ける」時代が到来したかのように見えました。

しかし、実際にAIコーディングエージェントを本格的な開発プロジェクトに導入した開発者たちは、すぐに別の課題に直面することになります。

## 「AIの監督役」という逆説

taktの作者であるnrs（成瀬允宣）は、3つのプロジェクトをAIエージェントと並行して進める中で、深刻な問題に気づきました。本来、AIに作業を委譲することで人間の負担を減らすはずが、実際には**人間がAIの監督役**になっていたのです。

### 監督コストの問題

AIコーディングエージェントは、作業中に頻繁に人間の介入を必要とします。

1. **質問への回答**: 「この関数の戻り値はどうすべきですか？」「テストフレームワークは何を使っていますか？」といった確認が発生する
2. **権限の許可**: ファイルの書き込み、コマンドの実行、外部APIへのアクセスなど、セキュリティ上の承認が必要になる
3. **方向性の修正**: AIが意図と異なる方向に実装を進めた場合、軌道修正が必要になる
4. **品質の検証**: 生成されたコードが要件を満たしているか、バグがないかの確認が必要

これらの監督タスクは、1つのプロジェクトであれば管理可能です。しかし、3つのプロジェクトを同時進行すると、常にいずれかのAIエージェントからの応答を待ち、対応する必要が生じます。人間がAIの「ボトルネック」になるという皮肉な状況です。

### コンテキストスイッチの代償

さらに深刻なのは、プロジェクト間のコンテキストスイッチです。AIエージェントからの質問に答えるためには、そのプロジェクトのコードベース、設計方針、現在の進捗状況を頭に入れている必要があります。プロジェクトAのAIに指示を出した直後にプロジェクトBのAIから質問が来ると、思考の切り替えに時間がかかり、両方のプロジェクトの効率が低下します。

```
[従来のAIエージェント作業フロー]

開発者 ←→ AI Agent (Project A)
  ↕
開発者 ←→ AI Agent (Project B)
  ↕
開発者 ←→ AI Agent (Project C)

→ 常に3つのプロジェクトの文脈を切り替えながら監督
→ AIの質問・承認待ちが人間の時間を奪う
```

## 既存アプローチの限界

この問題に対して、当時のAIコーディングツールはいくつかのアプローチを提供していましたが、いずれも根本的な解決には至りませんでした。

### アプローチ1: 自律性の向上

一つの方向性は、AIエージェントにより多くの自律性を与え、人間の介入を最小化することです。権限を広く付与し、AIに判断を委ねます。

**問題点**: 自律性が高いほど、AIが意図しない行動を取るリスクも高まります。テストのないコードをコミットしたり、セキュリティ上の脆弱性を含むコードを生成したり、アーキテクチャの方針から逸脱したりする可能性があります。品質を犠牲にして速度を得るトレードオフは、本格的な開発プロジェクトでは受け入れがたいものです。

### アプローチ2: 詳細なプロンプトエンジニアリング

もう一つの方向性は、プロンプトを精緻に作り込み、AIの行動を言葉で制御しようとすることです。「テストを必ず書くこと」「セキュリティを考慮すること」「コーディング規約に従うこと」といった指示を詳細に記述します。

**問題点**: プロンプトによる制御は「お願い」であり「強制」ではありません。AIは指示を忘れたり、解釈を誤ったり、コンテキストウィンドウの制約で指示が欠落したりします。また、プロンプトが長大になるほど、各指示の遵守率は低下する傾向があります。さらに、プロンプトの管理自体が複雑になり、プロジェクト間での共有や更新が困難になります。

### アプローチ3: マルチエージェントフレームワーク

複数のAIエージェントを協調させるフレームワーク（LangGraph、CrewAI、AutoGenなど）も登場していました。エージェント間でタスクを分担し、自律的に協調させるアプローチです。

**問題点**: これらのフレームワークの多くは、エージェントの協調方式自体をAIに判断させます。「どのエージェントにタスクを振るか」「次にどのステップに進むか」をAI自身が決定するため、実行のたびに異なるフローが発生します。再現性が低く、品質の保証が難しいという課題があります。

## 「再現可能な開発ワークフロー」という解

これらの問題を分析した結果、nrsは一つの洞察に至りました。

> **AIエージェントに必要なのは「自由」ではなく「構造」である。**

優れたソフトウェア開発チームを観察すると、各メンバーが完全に自由に行動しているわけではないことに気づきます。コーディング規約があり、コードレビューのプロセスがあり、テストの基準があり、デプロイのフローがあります。これらの「構造」が品質を担保しているのです。

AIエージェントにも同じ原則を適用すべきだ——これがtaktの出発点です。

### taktが目指す世界

```
[taktによる作業フロー]

開発者 → takt に指示を出す（1回）
         ↓
       takt が Piece（ワークフロー）を実行
         ↓
       ┌─ coder ペルソナがコードを書く
       │    ↓
       ├─ reviewer ペルソナがレビューする
       │    ↓ (問題あり → coderに差し戻し)
       │    ↓ (問題なし → 次へ)
       ├─ security-reviewer がセキュリティ検証
       │    ↓
       └─ supervisor が最終承認
         ↓
       自動でPR作成・レポート生成

→ 人間は最初の指示と最終確認だけ
→ 中間の監督はtaktのルールが担う
```

taktは、人間がワークフローを**事前に定義**し、AIエージェントがその定義に**厳密に従って**実行する仕組みを提供します。これにより以下が実現されます。

1. **監督コストの削減**: AIへの指示は最初の1回だけ。中間ステップの判断はtaktのルールエンジンが担う
2. **品質の一貫性**: コードレビュー、セキュリティ検証、テスト確認などのステップが必ず実行される
3. **再現性**: 同じPieceを使えば、誰が実行しても同じフローが保証される
4. **並行作業の効率化**: 複数のtaktプロセスを同時に走らせても、人間の介入は不要

## ソフトウェア開発プロセスからの着想

taktの設計は、ソフトウェア開発の歴史から多くの着想を得ています。

### CI/CDパイプラインとの類似性

CI/CD（継続的インテグレーション/継続的デリバリー）は、ビルド・テスト・デプロイのフローを自動化する仕組みです。GitHub ActionsやJenkinsのパイプライン定義は、「どのステップを、どの順序で、どの条件で実行するか」をYAMLで宣言的に記述します。

taktのPieceは、CI/CDパイプラインと同じ思想をAIエージェントの作業フローに適用したものです。ただし、CI/CDが「ビルドツールの実行」を自動化するのに対し、taktは「AIエージェントの思考と行動」を統制するという、より高度な制御を行います。

### コードレビュープロセスの形式化

多くの開発チームでは、プルリクエストに対して複数のレビュアーが異なる観点（設計、品質、セキュリティ）からレビューを行います。taktの並列Movementは、この人間のコードレビュープロセスをAIエージェントで再現したものです。

### ワークフローエンジンの発展

ビジネスプロセス管理（BPM）の分野では、ワークフローエンジンが業務フローの定義・実行・監視を担ってきました。taktはこのワークフローエンジンの概念を、AIエージェントの領域に持ち込んだとも言えます。

## まとめ: 構造がもたらす自由

一見矛盾するように聞こえますが、taktの「構造による統制」は、開発者に**真の自由**をもたらします。

AIエージェントの行動が予測可能になることで、開発者は安心して作業を委譲できます。監督の負担が減ることで、本来注力すべき設計や要件定義に時間を使えるようになります。ワークフローがコードとして管理されることで、チーム全体の開発プロセスが透明化され、継続的に改善できるようになります。

taktは「AIを制限するツール」ではなく、「AIと人間の協業を最適化するツール」なのです。
