## プロンプト管理の課題

AIコーディングエージェントを効果的に活用するためには、精緻なプロンプト設計が不可欠です。しかし、プロンプトが複雑化するにつれて、管理上の深刻な課題が顕在化してきます。

### モノリシックプロンプトの問題

一般的なAIエージェントの運用では、プロンプトは一つの長大なテキストとして管理されます。

```markdown
# 典型的なモノリシックプロンプト

あなたはシニアフルスタックエンジニアです。TypeScript/React/Node.jsに精通しています。

## コーディング規約
- 変数名はcamelCaseを使用
- 関数は30行以内に収める
- テストカバレッジ80%以上
- ESLintルールに準拠

## 今回のタスク
ユーザー認証機能を実装してください。

## ドメイン知識
- 既存のユーザーモデルはsrc/models/user.tsにあります
- 認証にはJWTを使用しています
- セッション管理はRedisで行っています

## 出力フォーマット
- 変更したファイルの一覧を最初に示す
- 各ファイルの変更理由を説明する
```

このアプローチには以下の問題があります。

1. **保守コストの増大**: プロジェクトが成長するにつれて、プロンプトが肥大化し、管理が困難になる
2. **関心事の混在**: 「誰が」「何のルールで」「何を」「何の知識を使って」「どう出力するか」が一つのテキストに混在する
3. **再利用の困難**: 異なるタスクで同じコーディング規約を使いたくても、プロンプト全体をコピーする必要がある
4. **変更の波及**: コーディング規約を変更したい場合、すべてのプロンプトを個別に更新する必要がある
5. **チーム協業の障壁**: 複数人がプロンプトを編集すると、コンフリクトが頻発する

## ファセットプロンプティングとは

**ファセットプロンプティング**（Faceted Prompting）は、Anthropicが提唱したプロンプト設計パターンで、プロンプトを**5つの独立した関心事（ファセット）**に分離する手法です。taktはこの設計パターンを全面的に採用し、`@anthropic-ai/faceted-prompting` ライブラリを通じて実装しています。

### 5つのファセット

```
┌────────────────────────────────────────────────────┐
│                  最終プロンプト                       │
│                                                    │
│  ┌──────────┐  ┌──────────┐  ┌──────────────┐     │
│  │ Persona  │  │  Policy  │  │ Instruction  │     │
│  │ 役割定義  │  │  方針    │  │   手順       │     │
│  └──────────┘  └──────────┘  └──────────────┘     │
│                                                    │
│  ┌──────────┐  ┌────────────────┐                  │
│  │Knowledge │  │Output Contract │                  │
│  │ 知識     │  │   出力規約     │                   │
│  └──────────┘  └────────────────┘                  │
└────────────────────────────────────────────────────┘
```

### 1. Persona（ペルソナ）— 役割と専門性

Personaファセットは、AIエージェントの**役割と専門性**を定義します。「あなたは何者か」に該当する情報です。

```markdown
# Persona: coder

あなたは実装を専門とするソフトウェアエンジニアです。

## 専門分野
- クリーンコードの原則に基づいた実装
- テスト駆動開発（TDD）
- リファクタリング

## 行動原則
- 既存のコードスタイルに合わせる
- 変更は最小限に留める
- テストを書いてからコードを書く
```

Personaファセットの特徴は**変更頻度が低い**ことです。一度定義すれば、プロジェクトが変わっても同じペルソナを再利用できます。taktでは25以上のビルトインペルソナが提供されており、ほとんどの開発シナリオをカバーします。

### 2. Policy（ポリシー）— コーディング規約と品質基準

Policyファセットは、プロジェクト全体に適用される**規約と基準**を定義します。「どのルールに従うか」に該当する情報です。

```markdown
# Policy: TypeScript プロジェクト規約

## コーディングスタイル
- strictモードを使用
- any型の使用を禁止
- 関数はアロー関数で統一
- importの順序: 外部 → 内部 → 相対

## テスト基準
- 新規コードのカバレッジ: 80%以上
- E2Eテスト: 主要フローに必須
- テストフレームワーク: Vitest

## セキュリティ基準
- ユーザー入力は必ずバリデーション
- SQLインジェクション対策必須
- 機密情報のハードコーディング禁止
```

Policyファセットの最大の利点は、**一箇所を変更すれば全Pieceに反映される**ことです。例えば、テストフレームワークをJestからVitestに移行する場合、Policyファイルを1つ更新するだけで、すべてのPieceでこの変更が自動的に適用されます。

### 3. Instruction（インストラクション）— Movement固有の手順

Instructionファセットは、特定のMovementでAIが実行すべき**具体的な手順**を定義します。「今、何をするか」に該当する情報です。

```yaml
# Piece定義内のinstruction_template
instruction_template: |
  以下のタスクを実装してください。

  ## タスク
  {task}

  ## 実装手順
  1. 既存のコードを読んで現状を理解する
  2. テストを先に書く
  3. テストが通るように実装する
  4. リファクタリングする

  ## 注意事項
  - 既存のAPIとの互換性を維持すること
  - パフォーマンスへの影響を考慮すること
```

Instructionファセットは**変更頻度が最も高い**ファセットです。タスクごとに異なる指示が必要であり、Movement定義の `instruction_template` として直接記述されます。

### 4. Knowledge（ナレッジ）— ドメイン知識

Knowledgeファセットは、AIエージェントがタスクを遂行するために必要な**ドメイン固有の知識**を定義します。「何を知っておくべきか」に該当する情報です。

```markdown
# Knowledge: 認証システムアーキテクチャ

## 概要
本プロジェクトの認証システムはJWTベースの認証を採用しています。

## コンポーネント
- AuthService (src/services/auth.ts): 認証ロジック
- UserModel (src/models/user.ts): ユーザーデータモデル
- AuthMiddleware (src/middleware/auth.ts): リクエスト認証

## データフロー
1. クライアントがログインAPIにリクエスト
2. AuthServiceがCredentialを検証
3. JWTトークンを発行して返却
4. 以降のリクエストはAuthMiddlewareがトークンを検証

## 制約
- トークン有効期限: 24時間
- リフレッシュトークン: 30日間
- 同時セッション数: 最大5
```

Knowledgeファセットは、プロジェクトのアーキテクチャや設計ドキュメントから生成できます。AIエージェントが「正しい文脈」でコードを書くための前提知識を提供します。

### 5. Output Contract（アウトプットコントラクト）— 出力規約

Output Contractファセットは、AIエージェントの出力が従うべき**フォーマットと構造**を定義します。「どう出力するか」に該当する情報です。

```markdown
# Output Contract: コードレビュー

## 出力フォーマット
レビュー結果は以下のフォーマットで出力してください。

### 変更サマリー
変更の概要を1-2文で記述

### 問題点
発見された問題を重要度順にリスト

### 改善提案
各問題に対する具体的な修正案

### 総合評価
- approved: 問題なし、マージ可能
- needs_fix: 修正が必要
- needs_discussion: 設計レベルの議論が必要
```

Output Contractは、Phase 3のステータス判定で特に重要です。AIの出力がOutput Contractに従うことで、taktのエンジンがステータスタグを正確に解析でき、確定的な遷移が実現されます。

## ファセットの組み立てプロセス

taktの命令構築層（Layer 6）は、5つのファセットを以下のプロセスで組み立てます。

```
[ファセットの収集]
    │
    ├── Persona:    Piece定義のpersonas → 対応するMarkdownファイルを読み込み
    ├── Policy:     グローバル設定 + プロジェクト設定から読み込み
    ├── Instruction: Movement定義のinstruction_template + テンプレート変数の展開
    ├── Knowledge:  プロジェクト設定から読み込み（オプション）
    └── Output Contract: エンジン内部で自動生成 + ユーザー定義（オプション）
        │
        ▼
[ファセットプロンプティングライブラリ]
    │ @anthropic-ai/faceted-prompting
    │ 各ファセットを最適な構造で統合
    ▼
[最終プロンプト]
    │ Phase 1（メイン実行）に送信
    ▼
AIプロバイダーへ
```

### 自動生成される要素

taktのエンジンは、いくつかの要素を**自動的に生成**してプロンプトに挿入します。

1. **ステータスマーカーの説明**: Phase 3で使用するステータスタグのフォーマットと選択肢
2. **コンテキスト情報**: イテレーション回数、前のMovementの情報など
3. **制約条件**: `edit` フラグに基づくファイル操作の制約

これにより、Persona定義にステータス判定ロジックを書く必要がありません。ペルソナは「専門家としての振る舞い」に集中でき、ワークフロー制御はエンジンが担います。

## ファセット分離の実践的メリット

### 1. コーディング規約の一括変更

チームがPrettierの設定を変更した場合、Policyファイルを1つ更新するだけです。

```markdown
# 変更前
## フォーマット
- インデント: タブ
- セミコロン: なし

# 変更後
## フォーマット
- インデント: スペース2つ
- セミコロン: あり
```

この変更は、Policyファセットを参照するすべてのPieceに自動的に反映されます。

### 2. ペルソナの使い回し

同じ `security-reviewer` ペルソナを、Web APIプロジェクト、モバイルアプリプロジェクト、インフラプロジェクトの異なるPieceで使い回せます。ペルソナの「セキュリティの専門家としての視点」はプロジェクト横断で共通であり、プロジェクト固有の知識はKnowledgeファセットで補完されます。

### 3. チームメンバーの分業

```
チームリーダー    → Persona定義の作成・管理
テックリード      → Policy（コーディング規約）の策定
プロジェクトメンバー → Knowledge（ドメイン知識）の整備
ワークフロー設計者  → Piece定義（Instruction含む）の設計
```

各ファセットが独立しているため、異なるメンバーが並行して作業でき、コンフリクトが発生しにくくなります。

### 4. 段階的な導入

ファセットプロンプティングは、すべてを一度に導入する必要はありません。

1. まずPersonaとInstructionだけでPieceを作成する
2. プロジェクトに応じてPolicyを追加する
3. 必要に応じてKnowledgeを整備する
4. 出力品質の向上のためにOutput Contractを定義する

各ファセットは独立しているため、段階的に充実させることができます。

## Anthropicファセットプロンプティングライブラリ

taktは `@anthropic-ai/faceted-prompting` ライブラリを使用してファセットの統合を行います。このライブラリはAnthropicが公式に提供しているもので、ファセットの構造化と最適な配置を自動的に行います。

ライブラリは以下を担います。

- 各ファセットのテキストを構造化されたプロンプトセグメントに変換
- ファセット間の参照関係を解決
- AIモデルの特性に合わせたプロンプト配置の最適化
- 長大なプロンプトの適切な分割と統合

taktのユーザーがこのライブラリの存在を意識することは通常ありません。Piece定義とPersona定義を作成すれば、ファセットの統合はtaktのエンジンが自動的に行います。

## まとめ: 分離がもたらす秩序

ファセットプロンプティングは、プロンプトの「スパゲッティコード化」を防ぐ設計パターンです。ソフトウェア開発においてモジュール化が保守性を向上させるのと同様に、プロンプトのモジュール化は以下を実現します。

- **変更の局所化**: 一つの関心事の変更が他に波及しない
- **再利用性**: 汎用的なファセットをプロジェクト横断で活用できる
- **テスト容易性**: 各ファセットを独立して検証できる
- **スケーラビリティ**: プロジェクトの成長に合わせてファセットを拡充できる

taktにおいて、ファセットプロンプティングはPieceとMovementの構造と並ぶ、品質保証の重要な基盤です。
