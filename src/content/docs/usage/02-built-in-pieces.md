## 組み込みPiece

taktは、一般的な開発ワークフローをカバーする複数のビルトインPieceを提供しています。これらのPieceはそのまま使用することも、カスタマイズのベースとして利用することもできます。

### default — テストファースト開発

`default` はtaktのデフォルトPieceです。テスト駆動開発（TDD）のプラクティスに基づいた、最も包括的なワークフローを提供します。

```
plan → write_tests → implement → review → complete
```

#### フローの詳細

```
[plan]
  │ planner ペルソナ
  │ タスクの分析と実装計画の策定
  ▼
[write_tests]
  │ coder ペルソナ (edit: true)
  │ テストを先に書く
  ▼
[implement]
  │ coder ペルソナ (edit: true)
  │ テストが通るように実装
  ▼
[review]
  │ 複数のレビュアーペルソナ
  │ アーキテクチャ、品質、セキュリティの観点からレビュー
  │   ├── approved → complete
  │   └── needs_fix → implement (差し戻し)
  ▼
[complete]
  │ supervisor ペルソナ
  │ 最終承認・PR作成
  ▼
完了
```

#### defaultの設計思想

`default` Pieceは以下の原則を体現しています。

1. **テストファースト**: 実装前にテストを書くことで、要件を明確化し、品質を担保する
2. **多角的レビュー**: 複数の専門ペルソナが異なる観点からレビューする
3. **反復的改善**: レビューで問題が検出された場合、自動的に修正サイクルに入る

### frontend-mini — フロントエンド特化

フロントエンド開発に特化した軽量Pieceです。UIコンポーネントの実装とレビューに最適化されています。

```
implement → review → complete
```

`default` と比較してテスト作成ステップが省略されており、素早いイテレーションに適しています。フロントエンド特有の観点（アクセシビリティ、レスポンシブデザイン、パフォーマンス）を重視したレビューが行われます。

### backend-mini — バックエンド特化

バックエンド開発に特化した軽量Pieceです。API実装とビジネスロジックのレビューに最適化されています。

```
implement → review → complete
```

バックエンド特有の観点（セキュリティ、データ整合性、エラーハンドリング、パフォーマンス）を重視したレビューが行われます。

### dual-mini — フルスタック

フロントエンドとバックエンドの両方を扱う軽量Pieceです。

```
implement → review → complete
```

フロントエンドとバックエンドの両方の観点からレビューが行われ、API契約の整合性も検証されます。

### compound-eye — 複眼レビュー

**複眼**（compound eye）の名の通り、**複数のAIモデルで同じタスクを実行し、結果を比較**するPieceです。

```
[並列実行]
  ├── model-a (例: Claude opus)
  ├── model-b (例: Claude sonnet)
  └── model-c (例: OpenAI GPT-4o)
      │
      ▼
[比較・統合]
  │ 各モデルの結果を比較し、最も優れた実装を選択
  ▼
完了
```

#### compound-eyeのユースケース

1. **品質比較**: 異なるモデルの出力品質を比較し、最適な実装を選択
2. **バグ検出**: あるモデルが見逃したバグを別のモデルが検出する可能性を高める
3. **アプローチの多様化**: 同じ問題に対する異なるアプローチを比較検討
4. **モデル評価**: 新しいモデルの能力を既存モデルと比較して評価

### magi — 三位一体審議システム

アニメ「新世紀エヴァンゲリオン」に登場するMAGIシステムにインスパイアされた、3つの異なる視点からの意思決定Pieceです。

```
[並列審議]
  ├── MELCHIOR-1 (科学者)
  │   論理的・データ駆動の視点
  │
  ├── BALTHASAR-2 (育成者)
  │   チーム・人間中心の視点
  │
  └── CASPER-3 (現実主義者)
      実用的・現実的な視点
      │
      ▼
[多数決]
  │ 3つの視点の結果を多数決で集約
  ▼
最終判断
```

#### MAGIの3つの視点

| ペルソナ | 視点 | 重視する点 |
|---|---|---|
| **MELCHIOR-1** | 科学者 | 技術的正確性、データに基づく判断、理論的な最適性 |
| **BALTHASAR-2** | 育成者 | チームへの影響、保守容易性、学習コスト、コミュニケーション |
| **CASPER-3** | 現実主義者 | 実装コスト、スケジュール、リスク、現実的な制約 |

#### MAGIのユースケース

magiは**コードの実装**ではなく、**技術的な意思決定**に使用します。

```bash
takt --piece magi "マイクロサービスに移行すべきか、モノリスのまま最適化すべきか"
```

3つの異なる視点からの分析と多数決により、偏りのない意思決定を支援します。

### 専門領域Piece

taktはさらに、特定のドメインに特化したPieceも提供しています。

#### CQRS + Event Sourcing Piece

CQRS（Command Query Responsibility Segregation）とEvent Sourcingパターンに特化したPieceです。コマンド側とクエリ側の分離、イベントストアの設計、プロジェクション管理など、このアーキテクチャパターン特有のプラクティスを強制するワークフローを提供します。

#### Research Piece

リサーチ・調査に特化したPieceです。コード実装ではなく、技術調査、比較分析、PoC作成に最適化されたワークフローを提供します。

#### Infrastructure Piece（Terraform/AWS）

インフラストラクチャコード（IaC）に特化したPieceです。Terraform HCLやAWS CloudFormationの記述に最適化されており、セキュリティグループ設定、IAMポリシー、ネットワーク構成のレビューなど、インフラ特有の観点を組み込んだワークフローを提供します。

## 組み込みペルソナ

taktは25以上のビルトインペルソナを提供しています。各ペルソナは特定の専門分野に特化しており、Movement定義で指定することで利用できます。

### コアペルソナ

これらのペルソナは、ほぼすべてのPieceで使用される基本的なペルソナです。

#### planner — 計画策定

タスクの分析と実装計画の策定を専門とするペルソナです。コードベースを調査し、タスクの実行に必要な手順を具体的に計画します。

```yaml
- name: plan
  persona: planner
  edit: false
  instruction_template: |
    以下のタスクを分析し、実装計画を策定してください。
    {task}
```

**特徴**: コードベースの調査能力が高く、既存のアーキテクチャとの整合性を考慮した計画を立案します。

#### architect-planner — 設計計画

plannerの上位版で、アーキテクチャレベルの設計と計画を行います。大規模な変更や新機能の追加時に使用します。

**特徴**: 設計パターン、SOLID原則、モジュール境界の設計など、アーキテクチャの観点を重視します。

#### coder — 実装

コードの実装を専門とするペルソナです。計画に基づいて、実際のコードを書きます。

```yaml
- name: implement
  persona: coder
  edit: true
  instruction_template: |
    以下の計画に基づいてコードを実装してください。
    {previous_response}
```

**特徴**: クリーンコードの原則に従い、既存のコードスタイルに合わせた実装を行います。テストも含めて書くことができます。

#### supervisor — 最終検証

ワークフロー全体の最終検証と承認を行うペルソナです。すべてのレビューが通過した後に、全体的な整合性を確認します。

```yaml
- name: supervise
  persona: supervisor
  edit: false
  instruction_template: |
    すべてのレビュー結果を踏まえ、最終判断を行ってください。
    {previous_response}
```

**特徴**: 個別の問題ではなく、変更全体の整合性、影響範囲、リスクを俯瞰的に評価します。

### レビューペルソナ

異なる専門分野からコードをレビューするペルソナ群です。

#### ai-antipattern-reviewer — AIアンチパターン検出

**AIが生成したコード特有のバグやアンチパターン**を検出する、takt独自のペルソナです。

AIが生成するコードには、人間が書くコードとは異なる特有の問題パターンがあります。

| AIアンチパターン | 説明 |
|---|---|
| **幻覚インポート** | 存在しないライブラリやモジュールをimportする |
| **過剰抽象化** | 不必要に複雑な抽象化層を追加する |
| **コンテキスト汚染** | 前の会話の文脈が無関係なコードに影響する |
| **楽観的エラーハンドリング** | エラーケースを過度に楽観視する |
| **非標準パターン** | フレームワークの慣習から逸脱した独自パターン |

このペルソナは、これらのAI特有の問題を専門的に検出します。

#### architecture-reviewer — 設計品質

コードの設計品質を評価するペルソナです。

**評価観点:**
- SOLID原則の遵守
- デザインパターンの適切な使用
- モジュール間の結合度・凝集度
- 変更容易性・拡張性
- 既存アーキテクチャとの整合性

#### qa-reviewer — テスト品質

テストの品質とカバレッジを評価するペルソナです。

**評価観点:**
- テストカバレッジの十分性
- テストケースの網羅性（正常系・異常系・境界値）
- テストの可読性と保守性
- テストの独立性（テスト間の依存がないか）
- モック/スタブの適切な使用

#### security-reviewer — セキュリティ

セキュリティの観点からコードを評価するペルソナです。

**評価観点:**
- OWASP Top 10の脆弱性
- 入力バリデーション
- 認証・認可の実装
- 機密情報の取り扱い
- 依存ライブラリの脆弱性

### 専門ペルソナ

特定の技術領域に特化したペルソナ群です。

#### frontend-reviewer — フロントエンドレビュー

フロントエンド開発の観点からレビューします。

**評価観点:**
- アクセシビリティ（WCAG準拠）
- レスポンシブデザイン
- パフォーマンス（Core Web Vitals）
- SEO
- ブラウザ互換性

#### terraform-coder — インフラコード実装

Terraform HCLの記述を専門とするペルソナです。

**特徴:**
- HCLのベストプラクティスに従った記述
- モジュール設計
- 状態管理の適切な設定
- セキュリティグループとIAMポリシーの設計

#### その他の専門ペルソナ

taktは上記以外にも多数のペルソナを提供しています。`takt config` コマンドで利用可能な全ペルソナの一覧を確認できます。

## ペルソナの閲覧とエジェクト

### ビルトインペルソナの確認

ビルトインペルソナの内容（Markdownファイル）は、taktのインストールディレクトリ内に含まれています。内容を確認するには、以下の方法があります。

1. GitHubリポジトリの `src/` 配下を確認する
2. `takt config` で一覧を表示する

### ペルソナのエジェクト

ビルトインペルソナをカスタマイズしたい場合は、`/eject` コマンドでプロジェクトにコピーできます。

```bash
# インタラクティブモード内で
/eject coder
```

これにより、`coder` ペルソナのMarkdownファイルが `.takt/personas/coder.md` にコピーされます。コピーされたファイルを編集することで、プロジェクト固有のカスタマイズが可能になります。ビルトインペルソナは変更されないため、他のプロジェクトには影響しません。

## Pieceの選択ガイド

### ユースケース別の推奨Piece

| ユースケース | 推奨Piece | 理由 |
|---|---|---|
| 新機能の実装（品質重視） | `default` | テストファースト + 多角的レビュー |
| 小さなバグ修正 | `backend-mini` / `frontend-mini` | 軽量で素早い |
| UIコンポーネント追加 | `frontend-mini` | フロントエンド特有の観点 |
| API追加 | `backend-mini` | バックエンド特有の観点 |
| フルスタック変更 | `dual-mini` | 両方の観点 |
| 技術選定・比較 | `magi` | 3つの視点からの多数決 |
| モデル評価 | `compound-eye` | 複数モデルの比較 |
| インフラ変更 | Infrastructure Piece | IaC特有の観点 |

### 独自Pieceの作成

組み込みPieceがプロジェクトの要件に合わない場合は、[カスタマイズ](/usage/03-customization/)ガイドを参照して独自のPieceを作成できます。組み込みPieceをベースにカスタマイズすることも、完全に新しいPieceを作成することも可能です。
